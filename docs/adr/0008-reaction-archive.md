# ADR-0008: 아카이브 타임라인과 이모지 리액션

- 상태: 확정
- 날짜: 2026-11-18

## 맥락
초기 `answer_reactions`에는 유일 제약이 없었다. 이모지 5종(LOVE, TOUCHED, THANKS, FUNNY, HUG)과 Phase 2의 음성 리액션이 한 테이블을 쓴다.

## 결정
1. 한 사람이 한 답변에 여러 종류의 이모지를 달 수 있다. 같은 종류는 1건이다: `UNIQUE(answer_id, user_id, emoji_code)`. 음성 리액션은 이모지와 구분되는 부분 유니크 인덱스로 따로 정한다(Phase 2). 본인 답변에도 달 수 있다.
2. API는 멱등하게 둔다: 달기는 `PUT`(이미 있으면 그대로, `INSERT ... ON CONFLICT DO NOTHING`), 취소는 `DELETE`(없으면 그대로). 앱이 화면 상태를 보고 토글처럼 보이게 한다.
3. **서버 권한**: 공개 전 답변에는 리액션할 수 없다(서버가 거절). 요청자는 유효 멤버여야 하고, 시간 초과 공개라면 본인이 답변을 마쳤어야 한다.
4. 탈퇴한 사용자의 답변·리액션은 그대로 보인다. 리액션 목록의 작성자는 "탈퇴한 사용자"(보는 사람이 정한 호칭이 있으면 그것)로 표시한다(ADR-0002).
5. 타임라인은 `cycle_date` 내림차순 커서(키셋) 페이징이다(안정 정렬을 위해 id 보조 정렬).
6. 스키마 변경: `answer_reactions` 유일 제약 추가(기존 중복 정리 포함).
7. 디자인 참고 자료는 저장소에 포함하지 않는다. 분위기만 참고하고 형태·캐릭터·아이콘·문구는 복제하지 않으며, 글자 대비·크기는 접근성 불변식(CLAUDE.md §5)을 우선한다.

## 근거와 트레이드오프
- **토글 API의 위험**: "누르면 달고, 다시 누르면 취소"는 요청을 재시도하면 결과가 뒤집히는 비멱등 동작이다. PUT/DELETE로 나누고 토글은 앱이 맡는다.
- **DB 제약이 최종 방어선**: 앱에서만 막으면 동시 요청에 뚫리므로 유일 제약을 건다.
- **OFFSET 페이징**: 새 데이터가 들어오면 페이지가 밀려 중복·누락이 생기고 깊은 페이지가 느려 키셋 방식을 쓴다.
