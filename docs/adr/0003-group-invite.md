# ADR-0003: 그룹 생성·초대·멤버 호칭 (group)

- 상태: 확정
- 날짜: 2026-11-17

## 맥락
PLAN 1-2. 초기 스키마: `group_invites.invite_code CHAR(6) UNIQUE`(전체 기간 유니크), `group_members UNIQUE(group_id, user_id)`와 `status`(ACTIVE/LEFT), `family_nickname`(한 사람당 호칭 1개).

## 결정
1. **입장 승인**: 6자리 코드로 들어오면 `PENDING`이 되고 방장이 승인하면 `ACTIVE`가 된다. 승인 대기는 2일 후 만료된다. 방장에게 알림을 보낸다(푸시는 보조, 앱 안의 승인 대기 목록이 기준).
2. **코드**: 유효기간 5분(설정값), 그룹당 활성 코드 1개, 기간 내 다회용, `SecureRandom`, 활성 코드끼리만 유니크.
3. **입장 시도 제한**: 5분에 5번 실패 시 20분 잠금. 20분 잠금에 3번 걸린 사용자는 이상 사용자로 간주해 관리자에게 보고한다(자동 차단은 하지 않는다).
4. **방장 위임**: 탈퇴·이탈 시점에 직접 지정하고, 기본값은 가장 오래된 `ACTIVE` 멤버(가입 일시 → id 순). 탈퇴 요청 즉시 적용되고 복구해도 방장은 자동으로 돌아오지 않는다. 혼자 남은 방장의 방은 해산한다.
5. **링크 초대**: 이번 범위에서 제외한다. 사양(유효기간 18시간, 1회용, 방장 승인 생략, 수락 요청에서만 소진)은 `docs/tasks/invite-link.md`에 보류 상태로 보관한다. 출시 후 이용률을 보고 도메인 구매와 함께 결정한다.
6. **인원 상한 20명**, 입장 전 그룹 정보 비공개, 호칭은 보는 사람마다 따로 저장(`member_aliases`). 강퇴(`REMOVED`)된 사용자는 코드로 재입장할 수 없다.
7. **상한 도달 시**: 관리자에게 연락하는 메시지 화면을 제공한다(특수 방은 수동 대응).
8. **인원 상한 동시성**: 승인 트랜잭션에서 그룹 행을 `SELECT ... FOR UPDATE`로 잠근 뒤 `ACTIVE` 인원을 `COUNT`해 20 이상이면 `GROUP_FULL`. 인원 수 컬럼은 두지 않는다(최대 20행이라 세기가 저렴하고, 컬럼은 정합성 책임만 늘린다). 같은 잠금이 강퇴·이탈과도 줄을 세운다. 상한에 걸린 요청은 `PENDING`으로 남아 2일 만료까지 대기하고, 방장에게 관리자 문의 화면을 보여 준다.
9. **입장 시도 제한 설계**: 사용자당 상태 행을 `FOR UPDATE`로 잠가 동시 요청을 줄 세운다. 순서는 잠금 확인 → 코드 검증 → 실패 기록. 실패 기록은 별도 트랜잭션에서 커밋한 뒤 예외를 던진다. 잠금 해제·5분 창 만료는 다음 시도에서 시각을 비교해 계산한다(배치 없음). 성공해도 실패 횟수와 잠금 누적은 리셋하지 않는다(자기 그룹 코드로 성공을 끼워 넣는 우회 방지). 잠금 3회 누적 기간은 24시간.
10. 스키마 변경(V3): 활성 코드 부분 유니크 인덱스, `member_aliases`, 멤버 상태 `REMOVED`.

## 근거와 트레이드오프
- **코드 보호**: 코드를 해시로 숨기기보다 짧은 수명과 시도 제한으로 보호한다. 난수는 `SecureRandom`을 쓰고 UNIQUE 위반 시 재시도한다(서버 시계 기반 난수는 예측 가능).
- **방장 승인**: 코드 입력 전에는 그룹 정보를 전혀 보여주지 않으므로 오타나 무차별 입력이 곧바로 입장으로 이어질 수 있다. 승인 후 활성화로 이 위험을 막는다.
- **재입장 멱등성**: 이미 멤버인 사용자의 재요청은 오류 대신 성공으로 응답하고, 나간 뒤 재입장 시 기존 행을 재사용한다(`LEFT`와 강퇴 `REMOVED` 구분).
- **링크 초대 보류**: 도메인·유니버설 링크·디퍼드 딥링크가 필요해 범위가 크므로 1단계는 코드 입력과 공유 시트로 한다.
