# ADR-0004: 푸시 알림(FCM) 발송 방식과 기기 토큰

- 상태: **제안** (아래 "확정 대기" 2건을 오너가 확인하면 "확정")
- 날짜: 2026-11-18
- 학습 노트(옵시디언): `개발/Ieum/학습/0006-FCM-푸시알림과-기기토큰.md`

## 맥락
group-core의 입장 요청을 방장에게 푸시로 알리고, 승인·거절 결과를 요청자에게 알린다. `user_devices`는 `UNIQUE(user_id, fcm_token)`이라 같은 토큰이 서로 다른 사용자 행에 존재할 수 있다. 푸시는 보조 채널이고 앱 안의 승인 대기 목록이 기준이다.

## 오너의 답
| # | 답 | 판정 |
|---|---|---|
| A-1 | 코드 입장은 저장 후 발송. 링크 입장(후속)은 입장 사실을 발송. 발송 실패 처리는 모름. 실패를 어떻게 아는가? ACK/WatchDog은 적용하면 안 될 것 같다 | ○ 직감이 맞다. FCM은 종단 간 ACK가 없고 "접수"만 응답하며, 재전송은 스팸이 되고, 신뢰성은 DB 상태로 얻는다. 타임아웃(WatchDog에 해당)은 FCM 호출 구간에 적용 |
| A-2,3 | 모름 | 커밋 후 비동기 발송, 아웃박스 없음(노트 0006 §4) |
| B | 완전히 모름 | 노트 0006 §5, §6에 개념 정리 |

## 확정 대기
1. **발송 설계(질문 A)**: 서비스는 알림 대상 정보만 담은 이벤트를 발행하고, `@TransactionalEventListener(AFTER_COMMIT)` + 전용 스레드풀 `@Async`로 발송한다. FCM 호출에는 타임아웃을 둔다. 일시 오류(`UNAVAILABLE`, `INTERNAL`)에만 짧게 제한적으로 재시도할 수 있고(횟수·간격은 Worker가 제안), `UNREGISTERED`는 토큰을 삭제한다(REQUIRES_NEW). 발송 예외는 로그만 남기고 업무 트랜잭션에는 영향이 없다. 아웃박스는 만들지 않는다(서버 크래시 시 알림 1건 유실 수용). 알림 문구·data에는 개인정보를 넣지 않는다.
2. **토큰 소유(질문 B)**: 토큰은 한 번에 한 사용자에게만 속한다. 등록 시 같은 토큰의 다른 사용자 행을 정리하고(upsert로 소유 이전), 로그아웃 시 그 기기 토큰을 삭제하며, DB 제약 `UNIQUE(fcm_token)`을 최종 방어선으로 둔다(**스키마 변경 필요 → 오너 승인**). 같은 계정의 여러 기기는 각각 별도 토큰으로 두고 모두에게 보낸다.
