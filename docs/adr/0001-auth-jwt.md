# ADR-0001: 소셜 로그인과 JWT 인증 설계

- 상태: **확정**
- 날짜: 2026-11-17
- 학습 노트(옵시디언): `개발/Ieum/학습/0001-auth-jwt.md` — 개념 설명과 모범 답안. 레포 밖에 있다.

## 맥락
PLAN 1-1. 소셜 토큰을 서버가 검증해 자체 JWT를 발급한다. 현재 `SecurityConfig`는 stateless이고 JWT 필터가 없어 보호 API는 전부 401이다. `users`에는 `UNIQUE(oauth_provider, oauth_subject)`와 `deleted_at`이 있다. 모바일은 `NoopAuthTokenReader`만 있다.

## 질문과 오너의 답 (원문)
| # | 오너의 답 | 판정 |
|---|---|---|
| 1-1 흐름 | 앱이 카카오톡에 인증을 요청 → 사용자가 카카오톡에서 인증 → 카카오톡이 인증 정보를 우리 서버에 넘겨줌 | △ 마지막 단계가 틀림. 카카오는 앱에 토큰을 주고, **앱이** 서버에 전달한다 |
| 1-2 토큰 검증 | 모르겠다 | 모름 → 노트 §1 |
| 1-3 신규/기존 구분 | 구분 방법은 모르겠다. 온보딩은 첫 로그인 시, 기능 설명은 해당 버튼만 강조하고 말풍선으로 안내. 프로필 입력은 토큰이 서버에 넘어온 직후 | △ 구분은 `(provider, subject)` 조회. 온보딩 두 종류를 섞어 말함 |
| 1-4 만료 시 | 서버가 진행 내용을 임시 저장. 앱/서버 차이를 잘 모름 | ✗ 임시 저장 주체가 틀림 → 노트 §3 |
| 1-5 범위 | 카카오, 네이버만 | ⚠ Apple 문제(열린 결정 1) |
| 2-1 토큰 | Access=로그인 인증 토큰, Refresh=사용 중이면 로그인 시간 연장. 서비스 특성상 소폭 길게. 일반 기준은 모름 | ○ 개념 대체로 맞음. 길게 할 대상이 Refresh라는 점이 핵심 |
| 2-2 Refresh 저장 | 저장하면 안 될 것 같다. DB/Redis 차이 모름 | ✗ 서버는 **해시로 저장**해야 한다 → 노트 §4 |
| 2-3 기기 | 여러 기기 로그인 가능하되 동시 접속은 1대로 차단. 새 기기 로그인 시 기존 기기는 임시 저장 후 로그아웃. 데이터 표현은 모름 | △ 정책은 가능하나 비용 있음. 구현 대상은 Access가 아니라 Refresh 레코드 |
| 2-4 앱 저장소 | 모르겠다 | 모름 → 노트 §5 |
| 3-1 탈취 | 탈취=계정 탈취. 토큰과 기기를 매칭해 확인. 기기·장소 목록을 사용자에게 제공 | △ 방향은 좋음. 표준 해법은 Rotation + 재사용 탐지 |
| 3-2 동시 401 | "3번"이라고 생각. 모르겠다 | ✗ 정답은 1번 (single-flight) |
| 3-3-1 카카오 장애 | 인증 실패로 응답. 자체 회원가입을 추가해 카카오와 연결하면 어떤가 | △ 장애는 401이 아니라 503. 자체 가입은 v1에 비추천 |
| 3-3-2 위조/만료 | 모르겠다 | 모름 → 노트 §7 |
| 3-3-3 탈퇴자 재로그인 | 일치하는 회원이 없으므로 신규 가입과 동일 | ○ 방향 맞음. 단 **현재 스키마에서는 재가입이 실패한다** (노트 §8) |
| 3-4 이중 가입 | 멱등성 개념인가? 막는 법은 모름 | ○ 개념 맞음 → 노트 §9 |

## 열린 결정 (오너가 답해야 확정됨)
1. **Apple 로그인**: 카카오·네이버만 제공하고 iOS 심사를 통과할 수 있는가? (App Store 정책 확인 필요, 노트 §10)
2. **Refresh 저장소**: PostgreSQL 테이블 vs Redis. 추천은 PostgreSQL (ARCHITECTURE.md는 Redis로 적혀 있어 문서 수정 필요).
3. **기기 정책**: 1기기만 vs 기기별 세션 목록 관리. `user_devices`(FCM 토큰, 다기기 전제)와 충돌하므로 같이 정해야 한다.
4. **토큰 수명**: Access 30분 / Refresh 30~90일(슬라이딩) 같은 수치.
5. **탈퇴 후 재가입**: 소프트 삭제 시 `(provider, subject)` 유니크 충돌 처리 방식.
6. **계정 연결**: 같은 사람이 카카오와 네이버로 각각 가입하면 별개 계정으로 둘 것인가?

## 최종 결정 (2026-11-17, 오너 확정)
1. **로그인 수단**: 카카오 · 네이버 · Apple 모두 구현한다. Apple은 첫 로그인 때만 주는 이름·이메일을 그때 저장하고, 탈퇴 시 Apple 토큰을 해지한다.
2. **Refresh 저장소**: PostgreSQL. 원문이 아니라 해시로 저장한다. Redis는 쓰지 않는다.
3. **기기 정책**: 기기별 세션(다기기 허용). Refresh Token Rotation + 재사용 탐지(family 폐기). 설정에서 "로그인된 기기 목록"과 "이 기기 로그아웃"을 제공한다. 위치(IP)는 v1에서 수집하지 않는다. *(AI 추천 채택)*
4. **토큰 수명**: Access 30분, Refresh 60일 슬라이딩. *(AI 추천 채택)*
5. **탈퇴**: 소프트 삭제 후 **30일 유예 기간 내 재로그인 시 복구**. 30일이 지나면 개인정보를 파기한다. 유예 중 그룹 내 표시 방식은 account 작업지시서에서 정한다.
6. **계정 연결**: 한 사용자에 여러 로그인 수단을 연결한다. **이메일 일치로 자동 연결하지 않고**, 로그인된 상태에서 설정 화면으로만 연결한다. `(provider, subject)`는 `users`에서 분리해 `user_identities` 테이블로 옮긴다.

## 결과·후속 작업
- 작업지시서: `docs/tasks/auth.md`(로그인·JWT·세션), `docs/tasks/account.md`는 auth 머지 후 작성(탈퇴·복구·계정 연결 UI).
- 스키마 변경(`V2`: `user_identities`, `refresh_tokens`)은 오너 승인 후 진행한다.
- `ARCHITECTURE.md`의 Redis(Refresh Token) 기술을 이 결정에 맞게 수정했다.
