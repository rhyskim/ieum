# ADR-0002: 탈퇴 파기와 계정 연결 (account)

- 상태: 확정
- 날짜: 2026-11-17

## 맥락
auth(ADR-0001)가 탈퇴 요청과 30일 복구까지 구현했다. 이후 파기 배치, 탈퇴 시 콘텐츠 처리, 계정 연결, Apple 토큰 해지가 남았다. `family_groups.creator_id`, `group_invites.inviter_id`가 `users`를 FK로 참조해 사용자 행을 그대로 삭제할 수 없다.

## 최종 결정
1. **파기 방식**: 익명화(tombstone). `users` 행은 남기고 이름·이메일·전화번호를 지우고 `PURGED`로 표시한다. `user_identities`, `refresh_tokens`, `user_devices`는 삭제한다.
2. **계정 연결**: 이미 다른 계정에 가입된 소셜 계정은 병합하지 않고 거절+안내한다. 마지막 로그인 수단은 해제할 수 없다.
3. **콘텐츠**: 탈퇴 요청 시 "상대에게 계속 공개 / 영구 삭제"를 선택해 저장하고, 실제 처리는 파기 시점에 실행한다. 리액션은 유지한다. 작성자는 "탈퇴한 사용자"로 표시하되, 보는 사람이 정한 별칭이 있으면 그것을 쓴다(ADR-0003의 호칭 모델).
4. **방장 탈퇴**: ADR-0003의 위임 규칙을 따른다.
5. **Apple 해지 실패**: 나머지 파기는 계속하고, 해지만 간격을 늘려 가며 재시도한다.
6. **복구와 파기 경쟁**: 복구 마감은 탈퇴 후 30일, 파기 시작은 31일 이후. 복구와 파기 시작은 같은 행에 대한 조건부 UPDATE로 한쪽만 성공시킨다.
7. **파기 배치**: ShedLock으로 서버 간 중복 실행을 막고, 사용자 1명 단위로 멱등 단계를 처리한다. 외부 자원(S3, Apple)을 먼저, DB는 마지막에 처리한다.

### 추가 결정 (2026-11-18)
8. **Root 가정 2가지 승인**: 복구 시 그룹이 이미 20명이면 그 그룹의 멤버십은 `LEFT`로 바꾼다. 혼자 남은 그룹은 파기 시점에 해산(`archive`)한다. 스키마 변경 V4(탈퇴 콘텐츠 선택, `purge_started_at`/`purged_at`, 이메일·전화 익명화용 제약 완화, Apple 해지 큐, `UNIQUE(user_id, provider)`)를 **승인**한다. Flyway 번호는 먼저 머지되는 쪽이 V4를 쓰고, 나중에 머지되는 쪽이 번호를 올려 조정한다(Root가 안내).
9. **파기 순서**: 음성(S3) 삭제 → DB 한 트랜잭션에서 익명화와 완료 표시. 서버가 중간에 죽으면 처음부터 다시 실행해도 안전하도록 모든 단계를 멱등으로 설계한다(`purge_started_at`은 처리 중 임대 표시, 30분 후 이어받기).
10. **중복 실행 방지**: ShedLock(서버 간) + 사용자 단위 조건부 UPDATE(2중 방어). 복구 마감 30일, 파기 시작 31일 이후로 구조적으로 겹치지 않게 하고, 조건부 UPDATE는 시계 차이에 대한 이중 방어로 둔다.
11. **유효 멤버 정의**: 코드 한 곳(공통 쿼리 조각)에서만 정의하고 모든 쿼리가 그것을 쓴다. 기존 파생 쿼리 메서드는 제거해 우회로를 없앤다. DB 뷰는 만들지 않는다.
12. **복구 시 상한 충돌**: 그룹 행 `FOR UPDATE`로 승인과 같은 줄을 서고, 여러 그룹은 id 오름차순으로 잠가 교착을 피한다.
13. **Apple 해지 재시도**: 큐에 쌓고 지수 백오프(10분×2^(n−1), 최대 24시간, ±20% 지터, 최대 8회 후 `FAILED`). 해지 실패는 나머지 파기를 막지 않는다. 이번 구현체는 키가 없어 "미설정 → 건너뜀"으로 기록한다.

### 추가 결정 (2026-11-18)
14. **영구 삭제(DELETE) 범위**: 본인이 쓴 답변(텍스트·음성 S3)만 삭제한다. 본인이 남에게 단 리액션은 선택과 무관하게 유지한다(작성자는 "탈퇴한 사용자" 또는 보는 사람의 호칭으로 표시). 삭제되는 답변에 달린 남의 리액션은 답변이 사라지므로 함께 사라진다. 계속 공개(KEEP)는 아무것도 지우지 않는다.
15. **방장 부재 그룹**: 방장이 파기될 때 그룹에 유효 멤버가 있으면 가장 오래된 유효 멤버(joined_at, id 순)에게 방장을 위임한다. 유효 멤버가 없으면 기존 "혼자 남은 그룹 해산" 규칙을 따른다. 사례: M 탈퇴 → O(방장) 탈퇴(후보 없어 방장 행 유지) → M 복구 → O 파기. (오너 선택 (a), 2026-11-18)
16. **복구 시 방장 부재 보정**: 복구하는 사용자의 그룹에 유효 방장이 없으면(방장이 파기됐거나 유예 중이라 숨겨진 경우) 복구자가 방장이 되고, 파기된 사용자의 방장 플래그는 해제한다. 결정 15의 남은 경로(M 탈퇴 → O 탈퇴 → O 파기 → M 복구)를 닫는다. (오너 선택, 2026-11-18)
