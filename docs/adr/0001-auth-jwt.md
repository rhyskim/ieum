# ADR-0001: 소셜 로그인과 JWT 인증 설계

- 상태: 확정
- 날짜: 2026-11-17

## 맥락
소셜 토큰을 서버가 검증해 자체 JWT를 발급한다(PLAN 1-1). 초기 상태는 `SecurityConfig`가 stateless이고 JWT 필터가 없어 보호 API가 전부 401이었다. `users`에는 `UNIQUE(oauth_provider, oauth_subject)`와 `deleted_at`이 있고, 모바일에는 토큰 저장 구현이 없었다.

## 결정
1. **로그인 수단**: 카카오 · 네이버 · Apple 서버 검증을 모두 구현한다. Apple은 첫 로그인 때만 주는 이름·이메일을 그때 저장하고, 탈퇴 시 Apple 토큰을 해지한다.
2. **Refresh 저장소**: PostgreSQL. 원문이 아니라 해시(SHA-256)로 저장한다. Redis는 쓰지 않는다.
3. **기기 정책**: 기기별 세션(다기기 허용). Refresh Token Rotation + 재사용 탐지(family 폐기). 설정에서 "로그인된 기기 목록"과 "이 기기 로그아웃"을 제공한다. 위치(IP)는 v1에서 수집하지 않는다.
4. **토큰 수명**: Access 30분, Refresh 60일 슬라이딩.
5. **탈퇴**: 소프트 삭제 후 30일 유예 기간 내 재로그인 시 복구한다. 30일이 지나면 개인정보를 파기한다(ADR-0002).
6. **계정 연결**: 한 사용자에 여러 로그인 수단을 연결한다. 이메일 일치로 자동 연결하지 않고, 로그인된 상태에서 설정 화면으로만 연결한다. `(provider, subject)`는 `users`에서 분리해 `user_identities` 테이블로 옮긴다.
7. **Refresh 동시 사용**: 유예 시간(leeway) 10초. 이미 사용된 Refresh가 사용 후 10초 안에 오면 같은 family에 새 토큰을 추가 발급하고, 10초가 지나면 family 전체를 폐기한다. 사용 처리는 `UPDATE ... WHERE used_at IS NULL` 조건부 갱신으로 원자적으로 한다.
8. **탈퇴 유예 중 로그인**: 자동 복구하지 않고 확인 단계를 거친다(`ACCOUNT_PENDING_DELETION` 응답 → 소셜 토큰 재검증 후 `restore`).

## 근거와 트레이드오프
- **토큰 검증 흐름**: 소셜 토큰은 제공자 → 앱 → 서버로 전달되며, 서버는 앱이 보낸 값을 신뢰하지 않고 제공자에 직접 확인한다(카카오는 `app_id` 일치까지 확인해 타 앱 토큰 재사용을 막는다).
- **Refresh를 해시로 저장**: DB가 유출돼도 원문 토큰으로 세션을 탈취할 수 없다. 저장소로 PostgreSQL을 택한 이유는 사용자 단위 조건부 UPDATE와 트랜잭션이 필요하고 별도 인프라를 늘리지 않기 위해서다.
- **재사용 탐지**: 탈취된 Refresh가 사용되면 정상 사용자의 다음 갱신이 재사용으로 감지된다. 동시 요청(앱이 401을 동시에 여러 번 받는 경우)과 구분하기 위해 짧은 유예 시간을 둔다. 모바일은 갱신을 single-flight로 한 번만 보낸다.
- **탈퇴 후 재가입**: 소프트 삭제 상태에서는 `(provider, subject)` 유니크 충돌로 재가입이 실패하므로, 유예 기간 복구와 식별정보 분리를 함께 설계했다.
- **카카오 장애**는 401이 아니라 503으로 구분한다.
